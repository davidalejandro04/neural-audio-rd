Native preview and paired-reference inference

The local software now includes a native ONNX renderer, persistent recurrent state export, a JUCE standalone/VST3 build, and an exploratory paired-reference control encoder. The completed P3 result remains negative overall. These extensions implement the next development steps; they do not fabricate the human or real-recording evidence needed for research/release acceptance.

Run the ready-built preview

From the repository root, in either Command Prompt or PowerShell:

.\exports\preview-v2\Launch-NeuralFX.cmd

The launcher loads the v2 128-sample distortion model. Select 48,000 Hz in the standalone audio-device settings. The app has Drive and Mix controls, a model chooser, and Load reference preset. The supplied reference preset is exports/preview-v2/presets/reference-example.json; it was inferred from a synthetic paired distortion reference. Use presets with the appropriate effect model.

The plugin processes mono or stereo, with independent per-channel state. The fixed-block adapter reports one model block of latency: 128 samples, or about 2.67 ms, for the supplied default model. The core has no lookahead; buffering adds this host latency. Model loading happens outside audio processing. Previous model instances are retained until resources are released, so the audio callback does not delete a graph when a model is changed. Model transitions and fast automation are not yet smoothed. The API supports up to 32 retained model selections between resource-release cycles.

For an offline example, play demo-input.wav and demo-rendered.wav in the preview folder. They are nine seconds of original algorithmic notes, not recordings of a guitar or evidence of real-hardware fidelity. To render your own mono 48 kHz WAV:

.\exports\preview-v2\Renderer\nafx-render.exe render --model exports/preview-v2/models/conditional_tcn-128.onnx --input path/to/dry.wav --output runs/my-native-render.wav --drive 0.5 --mix 1

The renderer supports ordinary mono PCM8/16/24/32 and IEEE float32 WAV input and writes float32 WAV output. It does not automatically resample, downmix, normalize levels, or support all extensible-WAV variants. Final partial blocks are padded and cropped, preserving input length. Rendering with --buffered --host-block 113 instead exercises the plugin-style fixed-latency adapter.

Control generalization v2

The historical models learned a dependence on both Drive and Mix even though their output already applied a mix residual. The new opt-in wet_only_conditioning=true predicts the fully wet path from Drive and applies Mix once at output. It obeys the exact law y(x,d,m) = (1-m)x + m y(x,d,1), including recurrent state, and retains the original behavior by default for historical checkpoints.

The new development protocol uses mixed controls in training and unseen-drive, unseen-mix and combined validation/test settings, with a new data seed. Its single 2,617-parameter TCN achieved test ESR 0.00236, MR-STFT 0.11088 and streaming error below 1e-6. The original PyTorch runtime gate failed (p99 budget fraction 0.788 against 0.7) and stays recorded. Its exported native checks passed. Training size, network width, seed and budget also changed, so this is not a controlled ablation or proof of superiority over P3. The new protocol requires further seed/data replication before broader claims.

python -m neural_fx run --config configs/control_generalization_v2.json --output runs/my-control-v2 --export

The supplied preview uses the already executed v2 checkpoint; another training run is optional. Existing output directories are preserved.

P4 baseline: learn controls from a reference pair

The encoder uses 22 paired dry/wet summary features (levels, correlation, residual, band-power ratios and moments), a small MLP with an eight-dimensional latent, a control-reconstruction loss and a within-preset source-consistency loss. Feature normalization is fit on training data only; the checkpoint is selected using validation control MSE. The synthetic training, validation and test sources are disjoint and use different control grids.

It was trained once on configs/reference_transfer.json. Across 72 cross-content trials over 12 test sources, the known-DSP decoder produced source-median ESR 0.01616 and MR-STFT 0.21577. The fixed no-reference Drive=0.5/Mix=1 baseline scored 0.66332 and 1.11332; the stronger training-mean controls baseline scored 0.16058 and 0.63497. Same-effect latents were closer than different-effect latents in 95.8% of the sampled comparisons. These are exploratory synthetic results, not significance or listening claims.

The encoder's inferred controls can drive a frozen conditional neural checkpoint or be loaded as a plugin preset. The measured DSP-decoder scores must not be attributed to the frozen neural decoder without evaluating that decoder separately. The encoder requires an already aligned, sufficiently excited dry/wet reference pair at the training sample rate. It is not a wet-only reference encoder, a jointly trained latent-conditioned HyNeFX model, or a multi-device effect embedding.

python -m neural_fx train-reference --config configs/reference_transfer.json --output runs/my-reference

python -m neural_fx infer-reference --encoder runs/reference-v1/reference.pt --reference-dry path/to/reference-dry.wav --reference-wet path/to/reference-wet.wav --output runs/my-reference-preset.json

python -m neural_fx render-reference --encoder runs/reference-v1/reference.pt --checkpoint runs/control-v2/models/conditional_tcn/best.pt --reference-dry path/to/reference-dry.wav --reference-wet path/to/reference-wet.wav --input path/to/new-dry.wav --output runs/my-transfer.wav

P5/P6: rebuild and verify

On Windows x64, install CMake and Visual Studio's C++ workload, then run from the repository root. SDK setup downloads pinned official archives and verifies their SHA-256 values. These Python commands work in either shell:

python -m neural_fx native-build --plugin
python -m neural_fx validator-build

python -m neural_fx native-validate --checkpoint runs/control-v2/models/conditional_tcn/best.pt --output runs/my-native-check --plugin build/native/plugin/NeuralAudioFX_artefacts/Release/VST3/NeuralAudioFX.vst3 --host-check build/native/plugin/nafx-plugin-check_artefacts/Release/nafx-plugin-check.exe

python -m neural_fx validate-plugin --plugin build/native/plugin/NeuralAudioFX_artefacts/Release/VST3/NeuralAudioFX.vst3 --model runs/my-native-check/128/model.onnx --output runs/my-validator-check

python -m neural_fx native-sustain --model runs/my-native-check/128/model.onnx --output runs/my-sustained-check.json --seconds 600

The native benchmark preallocates application buffers and uses one CPU thread. Its unpaced mode records computation time; paced mode uses a high-resolution Windows waitable timer and separately records processing-time misses and scheduling misses. The 600-second check covers the chosen mono model and block size, not every possible stereo host configuration. It uses a normal process thread rather than a real ASIO callback. A successful command reports completed measurement; inspect screening_passed, sustained_scheduling_passed, processing_deadline_misses and scheduling_deadline_misses.

To check a GRU/hybrid checkpoint, pass its best.pt to native-validate. The modern ONNX exporter carries both audio history and GRU hidden state explicitly. Do not zero hidden state between calls. Static block sizes may unroll recurrent operations into the exported graph; inspect runtime and artifact size rather than assuming a fused GRU kernel.

To assemble another local bundle from accepted parity evidence:

python -m neural_fx package-preview --validation runs/my-native-check --output exports/my-preview --reference-preset runs/my-reference-preset.json

The bundled runtime uses a private DLL filename and loads relative to the owning executable/plugin, avoiding an incompatible system ONNX Runtime. Keep the entire VST3 folder and its private runtime together. No files have been installed into host locations or published. SDK/license notes are in THIRD_PARTY_NOTICES.md and the preview's licenses/ directory.

Remaining human and external acceptance

  1. DAW hosts: add the preview's VST3 folder to a host-scanned location (copy the entire bundle if the host requires installation), rescan, load the model, and check 48 kHz operation, mono/stereo routing, 64/128/256/512 buffers, reported latency, bypass and state save/reopen. The host tests performed here do not count as Ableton/Audacity records.
  2. Real captures: supply licensed paired dry/wet files and the source-level index documented in the data contract. Inspect latency, levels and provenance, then train/evaluate on source-disjoint performances. No hardware has been reamped in this session.
  3. Listening: prepare suitable-length real excerpts, freeze the ABX/MUSHRA-style protocol and exclusions, recruit actual listeners and analyze anonymized responses using the planned repeated-measures method. The ABX packager/scorer exists; no listener responses have been invented.
  4. Release engineering: audit allocations inside ONNX Runtime and host paths, perform sustained target-host scheduling tests and control-transition tests, verify licenses and source/weight artifacts, then review release acceptance.

Use the uncompleted manual acceptance template to record actual observations. Production readiness remains false while these requirements remain open. The original P3 criterion is not retroactively relaxed by a faster runtime or a later model revision.
