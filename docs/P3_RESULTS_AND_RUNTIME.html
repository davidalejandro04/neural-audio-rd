Completed P3 study: what follows

All six configurations and 24 model fits completed. The preregistered study was analyzed with no missing runs. P3 was not accepted, and production readiness remains false. This is a completed experiment with a negative overall result, not a training execution error. Preserve it rather than repeatedly rerunning the same study or changing its thresholds.

These numbers are not medians of the six printed summaries. They average presets within source, then training seeds within source, and finally take a median over 20 sources. Only three training seeds were sampled, all using the same synthetic dataset; bootstrap intervals remain exploratory. Held-out cabinet MR-STFT improvement has an interval crossing zero, so stronger claims about spectral control interpolation are unsupported.

Cabinet results need qualification: the conditional TCN's seed-3407 test ESR was 1.95 and strongly affects the average. Parameter counts were matched (6,138 vs 6,011), but temporal memory was not: the TCN has a 63-sample receptive field, the FIR has 129 taps, and the hybrid also has a recurrent path. The synthetic cabinet is itself a known 129-tap linear convolution. This supports testing appropriate convolutional structure; it does not demonstrate that GRU recurrence or neural modeling is necessary. The analytic convolution remains the exact control.

Why some gates failed despite small validation error

All models passed streaming equivalence. Validation evaluates familiar settings, while final testing also includes unseen drive/mix combinations. The matched conditional TCN failed distortion quality for seed 3407, and the full hybrid failed it for seed 1337. All full-hybrid cabinet fits passed the ESR threshold, but two cabinet TCN fits failed it; the study's engineering-quality flag combines both compared systems. CPU screening failed for the full hybrid in every configuration. Thus the combined study could not satisfy quality and runtime acceptance in two effect families.

P5: profile the exported runtime without retraining

Executed on 2026-10-22: all 12 existing nonrecurrent exports passed the 128-sample screen, with p99 times 0.163–0.224 ms and zero measured deadline misses. This used about 6.1–8.4% of the 2.667 ms deadline. The paired PyTorch runs were approximately 6.1–7.8 times slower at p99. These results support moving these particular exports toward native runtime validation; they do not validate recurrent exports or fix cross-seed quality failures. Full artifact hashes, timings and environments are in the P5 evidence snapshot.

python -m neural_fx benchmark-study --plan configs/p3-study/plan.json --output runs/p5-onnx-local --iterations 2000

Run from the repository root using either Command Prompt or PowerShell. No execution-policy change is needed. Use a fresh output directory. The command runs sequentially across the 12 existing conditional-TCN and hybrid-without-GRU ONNX exports. It checks export identity, replays all golden blocks while retaining history, then compares ONNX and PyTorch with the same active audio/drive controls, one CPU thread, 20 warmup blocks and 2,000 measured blocks. No training data, checkpoints or P3 gates are modified.

Outputs: summary.json, comparison.csv, and per-export reports with artifact hashes, environment, p99/worst time, budget fraction and deadline misses. The current exports use 128-sample blocks, with a 2.667 ms deadline at 48 kHz. Screening requires p99 no greater than 70% of that deadline and zero measured misses. Two thousand blocks represent about 5.33 seconds of audio processed without pacing; this is not ten minutes of native callback validation. Python dispatch and runtime output allocations are included. Input selection and finite checks are outside timed intervals.

A passing exported screen identifies a runtime candidate only. It cannot repair interpolation errors or retroactively pass P3. Full hybrid/GRU export still requires an adapter carrying recurrent hidden state; none is silently reset by this command. ONNX session/provider and thread controls follow the official API and thread-management documentation.

Implementation sequence after profiling

  1. Preserve the completed study. The snapshot is retained in reports/p3-completed-analysis.json. Runtime results are separate development evidence.
  2. Investigate control generalization on a new development protocol. Both drive and mix change in held-out settings. Separate drive-only and mix-only validation tests; test whether learned dependence on mix is necessary when output already applies an exact mix residual. Current data do not identify a unique cause. Choose architecture changes using development data and reserve new final test sources.
  3. Build the appropriate native processor. A finite-context conditional TCN is a distortion candidate; direct FIR convolution remains the cabinet reference. If retaining the full hybrid, implement explicit persistent-GRU export and compare its value against simpler FIR/TCN paths. Preserve numerical parity and measure allocations, other block sizes, reset behavior and sustained native deadlines.
  4. Expand data and transfer research. Obtain aligned, licensed real captures and implement reference transfer on a stable controllable backbone. Reference conditioning must not be used to conceal current control interpolation failures.
  5. Validate the release. Build the standalone/JUCE VST3, conduct listener studies, run the official validator and target DAW host checks. These phases have not yet been completed.
